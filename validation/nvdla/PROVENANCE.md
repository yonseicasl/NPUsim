   used `ext/chipyard/.conda-env/bin/verilator` (same version, 5.022,

4. Verilator flags: `-Wno-REDEFMACRO` (RTL harmlessly redefines
   `DESIGNWARE_NOEXIST` with the same effective value in two places;
   Verilator 5.x escalates this to a fatal error where older Verilator
   versions treated it as a warning) and `--timing` (Verilator's event-driven
   `#delay` scheduling — required because the RAM behavioral models use
   `assign #1 ...`; the alternative `--no-timing` flag *reproduces the same
   cycle count* but changes the functional output — see README.md "Known
   limitation").
5. C++ toolchain for the Verilated model: `g++ 12.4.0`, not `clang++`.
   `--timing` mode needs `verilated_timing.cpp`'s C++20 coroutines; GCC's
   `<coroutine>` header uses `__builtin_coro_*` builtins that this system's
   `clang++` doesn't accept the way GCC's libstdc++ expects. Passed via
   `VMAKE_PARAMS="CC=g++ CXX=g++"` and `VERILATOR_PARAMS="--compiler gcc ..."`.
6. A full clean of `ext/nvdla/outdir/nv_small/verilator/` (except the `test/`
   subdirectory) was required between build attempts — a stale
   `VNV_nvdla__ALL.a` from an earlier failed attempt silently omitted the
   object defining `VNV_nvdla::eval_step()` even though a byte-identical
   symbol existed in the freshly compiled `.o` on disk; the archive step
   itself wasn't re-triggered by `make`'s dependency tracking. Not
   root-caused further; the practical mitigation is "clean before every
   full rebuild," recorded here for repro.

# 2026-08-25 — CRC root cause, EMULATION-model binary, full golden set

## Root cause of the multi-Atomic-C CRC failures (2026-08-20 "Known limitation")

Proven by instrumentation and by fix, on the current build:

1. A `--trace` build (separate Mdir `outdir/nv_small/verilator_trace`, VCD) of the
   failing `dc_6x8x192_3x3x192x32_int8_0` shows `sc2mac_wt_a_data*` (the CSC->CMAC
   weight operand lanes) at ZERO for the whole run while `sc2mac_dat_a_data*`
   carries real values and every valid/credit handshake fires. The output geometry
   (write addresses, line/surface strides, beat count) is exactly the programmed
   SDP cube; only the values are zero. Inside CDMA's weight loader (`u_wt`),
   `dma_rd_rsp_vld` fires once per weight beat (6,912) but the 64-bit data stage
   (`wt_cbuf_wr_data_ori_w`) never leaves zero.
2. The data dies inside the MCIF read-response path, whose latency FIFOs are built
   on `nv_ram_*` wrappers backed by TSMC `RAMDP_*_E2` behavioral models. Those E2
   models shape their internal write pulse from `assign #1` delay chains driving
   transparent latches (`weclk_d0/d1/d2`, `wa_lat`, `wd_lat` in
   `RAM_BANK_RAMDP_*`); Verilator flagged exactly these arrays as MULTIDRIVEN
   ("multiple driving blocks with different clocking") at verilation. Under
   Verilator (both `--timing` and `--no-timing`) the pulse/latch choreography does
   not schedule as in an event-driven simulator: the array write never lands and
   reads return the initial zeros. The `RAMPDP_*_D2` models (used by CBUF) contain
   ZERO `#1` delays (plain `always @(posedge WECLK)`) and work correctly -- which
   is why the data path was unaffected.
3. Why the small trace passed: the FIFO's flop-based near-empty bypass carries data
   without touching the RAM. The boundary is not "C > 8" (2026-08-20 hypothesis)
   but "enough in-flight DBB beats to push the response FIFO onto its RAM path".
4. Fix: build with `+define+EMULATION`. That macro is consumed ONLY by the 93 RAM
   model files (0 hits in vmod/nvdla RTL) and swaps each hard-macro model for the
   simple synchronous behavioral model NVIDIA ships in the same file for exactly
   this purpose. No RTL or testbench semantics change.
   Binary: `outdir/nv_small/verilator_emu/VNV_nvdla`, same Verilator 5.022 /
   g++ 12.4.0 / `--timing` flags as the main build.
5. Cross-check that the bug was value-only (no timing effect): the EMULATION binary
   reproduces the previously-failing runs' tick counts EXACTLY
   (`dc_6x8x192`: 53,724 ticks fail == 53,724 ticks pass) and leaves the passing
   baseline untouched (`dc_1x1x8`: 18,000 ticks, 169 cycles, CRC 8f68a2ae).

## Golden set (EMULATION binary)

All 13 official nv_small `dc_*` traces plus `sdp_1x1x1_pass_through` now PASS their
embedded CRC. `golden_rtl_full.csv` (extract_golden.py --write) records per trace:
end-to-end cycles (same boundary definition as the 2026-08-20 point), start/end
ticks, CRC, and per-stream DBB physical/distinct bytes classified by the trace's
own memory map. Physical DBB traffic obeys, exactly, on every trace:

    input  = W x H x ceil(C/8) x 8        (Atomic-C padding)
    weight = ceil(K*C*R*S / 128) x 128    (128 B weight-fetch granule)
    output = Wo x Ho x ceil(K/8) x 8      (Atomic-K padding)
