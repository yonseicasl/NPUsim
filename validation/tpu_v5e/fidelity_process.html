세대 비교와 검증 전략

최종 목표는 TPU v7(Ironwood)에서의 정합성이지만, v7은 지금 쓸 수 없습니다. 그래서 접근 가능한 v5e와 v6e로 NPUsim을 검증하고 개선합니다. 이 방식이 정당하려면 v7의 구조 요소 가운데 무엇이 v5e·v6e에서 검증되고 무엇이 남는지 분명해야 합니다.

단계적 검증의 논리

v5e: 기본 모델

TensorCore 1개, 128×128 MXU, HBM2e의 가장 단순한 구성입니다. 시스톨릭 타이밍, HBM 스트리밍, XLA 프로그램·커널 비용, 커널 사이 겹침을 여기서 먼저 검증했습니다.

v6e: MXU 세대 변화만 분리

TensorCore 수와 2D torus는 v5e와 같고, MXU가 v7과 같은 256×256으로 바뀝니다. 그래서 v5e에서 맞춘 모델이 MXU 크기 변화를 따라가는지를 다른 변수 없이 확인할 수 있습니다. HBM 대역폭이 2배라 계산과 메모리의 균형점이 바뀌는지도 함께 봅니다.

v7: 새로 생기는 요소

칩렛 2개, FP8, HBM3E, 3D torus는 v5e·v6e에 없습니다. 이 요소들은 v7 결과에서 "검증 범위 밖"으로 분명히 적고, 접근이 생기면 이 항목부터 측정합니다.

설정을 만드는 방식은 같다

tpu_v5e.cfg는 tpu_v4.cfg에서 MXU 수, 클럭, HBM 대역폭만 바꿔 만들었습니다. v6e와 v7도 같은 방식으로 스펙 값만 바꾸고, 측정으로 얻는 값(프로그램·커널 비용)만 세대마다 다시 잽니다. 세대마다 맞춤 보정을 하지 않으므로, v5e·v6e에서 확인한 정합성은 공통 구조 요소에 대한 v7 예측의 근거가 됩니다. v7에만 있는 요소는 이 근거에 포함되지 않습니다.

TPU, JAX, XLA

TPU는 직접 프로그래밍하는 장치가 아닙니다. 사용자는 Python으로 계산을 적고, 컴파일러가 그것을 TPU 프로그램으로 바꿔 실행합니다. 측정값을 NPUsim과 비교하려면 이 경로에서 무엇이 실제로 실행되는지 알아야 합니다.

PYTHON계산을 NumPy처럼 적습니다. 예: a @ b
JAXjax.jit이 함수를 추적해 계산 그래프로 만듭니다.
XLA그래프를 최적화해 TPU용 프로그램으로 컴파일합니다.
TPU프로그램 안의 커널이 MXU, 벡터 유닛, HBM을 씁니다.

JAX

Google이 만든 Python 수치 계산 라이브러리입니다. NumPy와 거의 같은 문법(jax.numpy)으로 행렬 연산을 적으면, 같은 코드가 CPU, GPU, TPU에서 실행됩니다.

jax.jit으로 감싼 함수는 처음 호출할 때 컴파일되고, 이후에는 컴파일된 프로그램이 장치에서 바로 실행됩니다. 호출은 비동기라 Python이 결과를 기다리지 않고 다음 명령을 보내므로, 시간을 잴 때는 block_until_ready()로 끝날 때까지 기다려야 합니다.

XLA

JAX와 TensorFlow가 공통으로 쓰는 머신러닝 컴파일러입니다. 계산 그래프를 HLO라는 중간 표현으로 받아, 여러 연산을 하나의 커널로 합치고(fusion), 데이터를 HBM과 칩 안 메모리 중 어디에 둘지 정하고, TPU 명령으로 바꿉니다.

이번 측정에서 본 많은 현상이 XLA의 결정이었습니다. 칩 안에 들어가는 가중치를 먼저 복사해 두는 것, 반복 호출 사이에 입력을 남겨 두는 것, 다음 커널의 데이터를 미리 가져오는 것이 그 예입니다.

Colab에서 측정하기

Colab은 브라우저에서 쓰는 Jupyter 노트북 환경이고, 언어는 Python입니다. 런타임 유형을 v5e-1 TPU로 바꾸면 TPU v5e 칩 1개가 붙은 가상 머신이 배정되고, JAX가 미리 설치되어 있습니다. 측정 스크립트 measure_tpu.py는 JAX만 쓰는 Python 파일 하나라 별도 설치 없이 실행됩니다.

노트북 셀 순서

측정 코드의 핵심 (간략화)

import jax, jax.numpy as jnp

f = jax.jit(lambda a, b: a @ b)                       # GEMM 하나 = XLA 프로그램 하나
sets = [(rand((8, 4096)), rand((4096, 4096))) for i in range(16)]  # 서로 다른 버퍼 512 MB 이상
f(*sets[0]).block_until_ready()                          # 첫 호출: 컴파일

with jax.profiler.trace("traces/gemm", create_perfetto_trace=True):
    for i in range(n):
        out = f(*sets[i % len(sets)])                    # 호출마다 다른 버퍼
    out.block_until_ready()
# perfetto_trace.json.gz에서 TPU:0의 'XLA Modules'(프로그램)와 'XLA Ops'(커널, 복사) 시간을 읽음

NPUsim과 비교

내려받은 폴더를 서버의 validation/tpu_v5e/results/<날짜>/에 두고 compare_v5e.py를 실행합니다. 측정된 모든 형태를 NPUsim으로 다시 시뮬레이션해, 실측·NPUsim·roofline과 오차를 표로 내고 compare_gemm.csv에 저장합니다. 측정 조건에 따라 --in-program(루프 안 커널), --chain(연쇄 안 커널), --dram hbm2e_v5e.yaml(Ramulator2 DRAM)을 붙입니다.

진행 과정

  1. 공개 자료로 출발점 잡기

    11-02

    최신 TPU 세대는 구조 정보만 공개되어 있고, 커널 단위 실측값은 없었습니다. 구조와 실측이 함께 공개된 TPU v4 PaLM decode 지연(Pope 외, MLSys 2023)으로 먼저 비교했습니다.

    결과: NPUsim이 실측보다 41~60% 짧게 예측했습니다. 칩 안 GEMM은 roofline의 1.2~1.4배로 합리적이었으나, 공개 자료만으로는 나머지 시간이 통신·vector 연산·XLA 중 어디서 오는지 나눌 수 없었습니다.

  2. 측정 경로 정하기

    11-02 ~ 11-03
    • Kaggle TPU v5e-8: 무료지만 대기열이 7~14시간 이상이라 아직 배정되지 않았습니다.
    • TPU Research Cloud: 공개 사례로는 v4가 배정되어 PaLM 비교에 유리하지만, 승인 절차가 필요합니다.
    • Colab TPU v5e-1: 바로 쓸 수 있어 1칩 측정은 모두 여기서 했습니다.

    측정 스크립트(현재 1칩용 measure_tpu_v5e1.py와 8칩용 measure_tpu_v5e8.py)는 JAX만 쓰는 Python 파일로, GEMM·vector·collective·decode 레이어를 재고 profiler trace에서 장치 시간과 op별 시간을 읽습니다.

  3. 1차 측정에서 측정 착시 발견

    11-03

    큰 GEMM은 NPUsim과 잘 맞았지만(M ≥ 512 MAPE 9%), decode 형태 GEMM 일부가 HBM 대역폭의 3~4배 속도(2.7~3.3 TB/s)로 측정되었습니다.

    원인: 같은 버퍼로 반복 호출하면 가중치가 칩 안에 남아 재사용됩니다. 실제 decode에서는 매 토큰 서로 다른 레이어 가중치를 읽으므로 일어나지 않는 일입니다.
    조치: 호출마다 서로 다른 버퍼(합계 512 MB 이상)를 돌려 쓰도록 측정 방식을 바꿨습니다.

  4. 실효 HBM 대역폭 확인

    11-03

    버퍼를 돌려 쓰자, 칩 안에 들어가는 가중치는 먼저 통째로 복사한 뒤 계산하는 XLA 동작이 드러났습니다. 복사와 스트리밍은 형태와 관계없이 약 750 GB/s로 일정했고, 이후 순수 HBM 읽기 측정(732~757 GB/s, 공칭의 89~92%)으로 직접 확인했습니다.

    결정: 설정의 HBM 대역폭은 공개 스펙 819 GB/s로 유지했습니다. 8% 차이는 결과에 맞춰 바꿀 숫자가 아니라 DRAM 모델이 만들어야 할 효과로 보았습니다.

  5. MOSAIC Ramulator2와 함께 평가

    11-03

    v5e HBM2e를 64-bit pseudo-channel 32개(819.2 GB/s)로 설정하고, NPUsim의 DRAM 스트림을 Ramulator2로 시뮬레이션했습니다. 단독 측정에서 지속 대역폭은 675 GB/s(82%)였습니다.

    • 계산 병목 GEMM은 두 DRAM 모델의 결과가 같았습니다(DRAM 시간이 계산 뒤에 가려짐).
    • HBM 병목 GEMM은 analytic이 약 5% 짧게, Ramulator2가 약 5% 길게 예측해 실측을 사이에 둡니다.
    • NPUsim은 1 MiB 스트림마다 장치를 새로 만들어 1.5 µs만 시뮬레이션하므로, refresh(3.9 µs 주기)가 한 번도 일어나지 않는다는 것도 확인했습니다.
    바로잡은 것: strip 1→2개 사이 증가분으로 외삽했더니 8192³이 MXU 피크보다 빠르게 나왔습니다. 2→4개 기울기로 외삽하도록 고쳤습니다.

  6. 레이어 단위 검증

    11-03

    병렬 세션이 측정 구조를 보강해 세 차례 다시 쟀습니다. 레이어마다 가중치·KV 버퍼를 따로 두고, KV를 head 우선 레이아웃으로 바꿨습니다.

    • decode 레이어 전체: NPUsim + Ramulator2 MAPE 3.5%
    • attention: KV 읽기 이론 시간의 1.10배(약 745 GB/s). 앞서 본 1.25~3.6배는 KV 레이아웃과 슬라이스 복사 때문이었습니다.
    • int8 가중치 GEMM: M = 512에서 bf16과 같은 시간이 걸려, 역양자화 후 bf16으로 계산한다는 가정과 맞습니다.
    • 측정 사이 변동계수: 이어서 실행한 GEMM 0.8%

  7. 작은 커널의 고정 시간 측정

    11-04

    --only smallk 실험을 추가해, 커널을 단독으로 실행할 때와 한 프로그램 안에서 이어서 실행할 때의 고정 시간을 나눠 쟀습니다.

    실행 방식TPU 실측NPUsim 반영
    커널 하나를 단독 실행약 1.0 µs아래 두 값의 합
    프로그램당 한 번0.69 µsprogram_setup_cycle = 1035 (새 항목)
    프로그램 안에서 커널마다0.22 µslayer_setup_cycle = 330

  8. 레이어 사이 겹침 모델

    11-04

    TPU는 다음 커널의 가중치를 앞 커널이 끝나 가는 동안 미리 읽습니다. NPUsim은 레이어마다 파이프라인을 따로 채우고 비워, 연쇄 실행에서 GEMM마다 1~1.3 µs를 더 계산했습니다.

    각 레이어의 prologue(첫 타일이 PE에 닿기까지)와 tail(DRAM 단계가 끝난 뒤)을 기록하고, 네트워크를 합산할 때 경계마다 min(taili, prologuei+1)만큼 겹치게 했습니다(interlayer_overlap = 1). 다음 레이어의 계산은 앞 레이어가 끝난 뒤에 시작합니다.

    결과: 연쇄 실행 홀수 GEMM MAPE가 33.6%에서 11.9%로, M = 512는 2.7%로 줄었습니다. NPUsim 단위 테스트와 타임라인 검증을 통과했습니다.

  9. 활성값 칩 안 유지와 남은 오차 검토

    11-05

    연쇄 실행에서 TPU 커널은 가중치 바이트만큼만 시간이 걸렸습니다(100×1000: 2 MB를 2.81 µs, 712 GB/s). 앞 커널의 출력이 칩 안에 남아 다음 커널의 입력이 된다는 뜻입니다. NPUsim에 이미 있던 텐서 상주 기능을 일반 네트워크 경로에서도 쓰도록 activation_residency를 추가했습니다.

    결과: 연쇄 실행 홀수 GEMM MAPE가 analytic 11.9% → 6.4%, Ramulator2 23.4% → 4.1%로 줄었습니다. 큰 decode GEMM과 같이 analytic은 약간 짧게, Ramulator2는 약간 길게 예측합니다.
    • 단독 실행의 남은 오차는 XLA의 직렬 복사입니다. 겹침을 없앤 설정으로 시험하면 복사되는 형태는 −25% → +11%로 맞지만, 스트리밍 형태는 −2% → +40%로 틀어집니다. 조건부로만 맞는 XLA 동작이라 NPUsim에 넣지 않았습니다.
    • N = 1024 작은 GEMM이 길게 나오는 이유는 strip마다 DRAM 타일이 하나뿐이라 단계들이 겹치지 못하기 때문입니다. K를 DRAM 단계로 나누는 매핑은 prologue를 오히려 늘려(0.76 → 6.11 µs) 해결책이 아니었습니다.

작은 GEMM 오차의 변화

같은 측정 데이터에 대한 NPUsim MAPE입니다. 원은 처음 비교했을 때, 채운 점은 지금 값입니다.

처음 비교현재

단독 실행은 N < 512 매핑 수정, 커널당 0.22 µs, 프로그램당 0.69 µs가 차례로 반영되었습니다. 연쇄 실행은 레이어 사이 겹침과 활성값 칩 안 유지가 반영되었습니다.

판단 기준

스펙 값은 그대로 둔다

MXU 수, 클럭, HBM 대역폭은 공개 스펙을 유지했습니다. 실측 750 GB/s를 설정에 넣으면 원인을 모델링하지 않고 결과에 맞춘 것이 됩니다.

근거가 독립적인 값만 넣는다

설정에 넣은 실측값은 비교 대상과 다른 실험에서 얻었습니다. 예를 들어 0.69 µs와 0.22 µs는 연쇄 실행 측정에서 얻었고, K 스윕 오차에 맞춘 값이 아닙니다.

변수 여럿을 숫자 하나에 맞추지 않는다

refresh, 주소 매핑, 큐 깊이를 함께 돌려 92%에 맞추는 방식은 쓰지 않았습니다. 표준에 근거가 있는 refresh만 따로 시험했습니다.

측정 조건을 먼저 의심한다

오차가 클 때마다 먼저 측정이 실제 실행을 대표하는지 확인했습니다. 버퍼 재사용, 레이아웃 복사, 생략된 읽기가 모두 이렇게 걸러졌습니다.
