NPUsim을 TPU v5e 실측에 맞춰 검증하고 개선한 과정

공개 논문값과의 비교에서 시작해, Colab TPU v5e-1에서 직접 잰 커널·레이어 시간으로 NPUsim의 정합성을 평가했습니다. 측정 방식이 만든 착시를 하나씩 걸러 내고, 근거가 있는 항목만 모델에 반영했습니다.

기간 2026-11-02 ~ 11-05 장비 TPU v5 lite (v5e-1), JAX 0.11.2 브랜치 npusim tpu-measure @ 56fd804

진행 과정

  1. 공개 자료로 출발점 잡기

    11-02

    최신 TPU 세대는 구조 정보만 공개되어 있고, 커널 단위 실측값은 없었습니다. 구조와 실측이 함께 공개된 TPU v4 PaLM decode 지연(Pope 외, MLSys 2023)으로 먼저 비교했습니다.

    결과: NPUsim이 실측보다 41~60% 짧게 예측했습니다. 칩 안 GEMM은 roofline의 1.2~1.4배로 합리적이었으나, 공개 자료만으로는 나머지 시간이 통신·vector 연산·XLA 중 어디서 오는지 나눌 수 없었습니다.

  2. 측정 경로 정하기

    11-02 ~ 11-03
    • Kaggle TPU v5e-8: 무료지만 대기열이 7~14시간 이상이라 아직 배정되지 않았습니다.
    • TPU Research Cloud: 공개 사례로는 v4가 배정되어 PaLM 비교에 유리하지만, 승인 절차가 필요합니다.
    • Colab TPU v5e-1: 바로 쓸 수 있어 1칩 측정은 모두 여기서 했습니다.

    측정 스크립트 measure_tpu.py는 JAX 파일 하나로, GEMM·vector·collective·decode 레이어를 재고 profiler trace에서 장치 시간과 op별 시간을 읽습니다.

  3. 1차 측정에서 측정 착시 발견

    11-03

    큰 GEMM은 NPUsim과 잘 맞았지만(M ≥ 512 MAPE 9%), decode 형태 GEMM 일부가 HBM 대역폭의 3~4배 속도(2.7~3.3 TB/s)로 측정되었습니다.

    원인: 같은 버퍼로 반복 호출하면 가중치가 칩 안에 남아 재사용됩니다. 실제 decode에서는 매 토큰 서로 다른 레이어 가중치를 읽으므로 일어나지 않는 일입니다.
    조치: 호출마다 서로 다른 버퍼(합계 512 MB 이상)를 돌려 쓰도록 측정 방식을 바꿨습니다.

  4. 실효 HBM 대역폭 확인

    11-03

    버퍼를 돌려 쓰자, 칩 안에 들어가는 가중치는 먼저 통째로 복사한 뒤 계산하는 XLA 동작이 드러났습니다. 복사와 스트리밍은 형태와 관계없이 약 750 GB/s로 일정했고, 이후 순수 HBM 읽기 측정(732~757 GB/s, 공칭의 89~92%)으로 직접 확인했습니다.

    결정: 설정의 HBM 대역폭은 공개 스펙 819 GB/s로 유지했습니다. 8% 차이는 결과에 맞춰 바꿀 숫자가 아니라 DRAM 모델이 만들어야 할 효과로 보았습니다.

  5. MOSAIC Ramulator2와 함께 평가

    11-03

    v5e HBM2e를 64-bit pseudo-channel 32개(819.2 GB/s)로 설정하고, NPUsim의 DRAM 스트림을 Ramulator2로 시뮬레이션했습니다. 단독 측정에서 지속 대역폭은 675 GB/s(82%)였습니다.

    • 계산 병목 GEMM은 두 DRAM 모델의 결과가 같았습니다(DRAM 시간이 계산 뒤에 가려짐).
    • HBM 병목 GEMM은 analytic이 약 5% 짧게, Ramulator2가 약 5% 길게 예측해 실측을 사이에 둡니다.
    • NPUsim은 1 MiB 스트림마다 장치를 새로 만들어 1.5 µs만 시뮬레이션하므로, refresh(3.9 µs 주기)가 한 번도 일어나지 않는다는 것도 확인했습니다.
    바로잡은 것: strip 1→2개 사이 증가분으로 외삽했더니 8192³이 MXU 피크보다 빠르게 나왔습니다. 2→4개 기울기로 외삽하도록 고쳤습니다.

  6. 레이어 단위 검증

    11-03

    병렬 세션이 측정 구조를 보강해 세 차례 다시 쟀습니다. 레이어마다 가중치·KV 버퍼를 따로 두고, KV를 head 우선 레이아웃으로 바꿨습니다.

    • decode 레이어 전체: NPUsim + Ramulator2 MAPE 3.5%
    • attention: KV 읽기 이론 시간의 1.10배(약 745 GB/s). 앞서 본 1.25~3.6배는 KV 레이아웃과 슬라이스 복사 때문이었습니다.
    • int8 가중치 GEMM: M = 512에서 bf16과 같은 시간이 걸려, 역양자화 후 bf16으로 계산한다는 가정과 맞습니다.
    • 측정 사이 변동계수: 이어서 실행한 GEMM 0.8%

  7. 작은 커널의 고정 시간 측정

    11-04

    --only smallk 실험을 추가해, 커널을 단독으로 실행할 때와 한 프로그램 안에서 이어서 실행할 때의 고정 시간을 나눠 쟀습니다.

    실행 방식TPU 실측NPUsim 반영

    프로그램당 한 번0.69 µsprogram_setup_cycle = 1035 (새 항목)

  8. 레이어 사이 겹침 모델

    11-04

    TPU는 다음 커널의 가중치를 앞 커널이 끝나 가는 동안 미리 읽습니다. NPUsim은 레이어마다 파이프라인을 따로 채우고 비워, 연쇄 실행에서 GEMM마다 1~1.3 µs를 더 계산했습니다.

    각 레이어의 prologue(첫 타일이 PE에 닿기까지)와 tail(DRAM 단계가 끝난 뒤)을 기록하고, 네트워크를 합산할 때 경계마다 min(taili, prologuei+1)만큼 겹치게 했습니다(interlayer_overlap = 1). 다음 레이어의 계산은 앞 레이어가 끝난 뒤에 시작합니다.

    결과: 연쇄 실행 홀수 GEMM MAPE가 33.6%에서 11.9%로, M = 512는 2.7%로 줄었습니다. NPUsim 단위 테스트와 타임라인 검증을 통과했습니다.

작은 GEMM 오차의 변화

같은 측정 데이터에 대한 NPUsim MAPE입니다. 원은 처음 비교했을 때, 채운 점은 지금 값입니다.

처음 비교현재

단독 실행은 N < 512 매핑 수정, 커널당 0.22 µs, 프로그램당 0.69 µs가 차례로 반영되었습니다. 연쇄 실행은 레이어 사이 겹침이 반영되었습니다.

판단 기준

스펙 값은 그대로 둔다

MXU 수, 클럭, HBM 대역폭은 공개 스펙을 유지했습니다. 실측 750 GB/s를 설정에 넣으면 원인을 모델링하지 않고 결과에 맞춘 것이 됩니다.

근거가 독립적인 값만 넣는다

설정에 넣은 실측값은 비교 대상과 다른 실험에서 얻었습니다. 예를 들어 0.69 µs와 0.22 µs는 연쇄 실행 측정에서 얻었고, K 스윕 오차에 맞춘 값이 아닙니다.

변수 여럿을 숫자 하나에 맞추지 않는다

refresh, 주소 매핑, 큐 깊이를 함께 돌려 92%에 맞추는 방식은 쓰지 않았습니다. 표준에 근거가 있는 refresh만 따로 시험했습니다.

측정 조건을 먼저 의심한다

오차가 클 때마다 먼저 측정이 실제 실행을 대표하는지 확인했습니다. 버퍼 재사용, 레이아웃 복사, 생략된 읽기가 모두 이렇게 걸러졌습니다.

남은 작업

  • 8칩 collective와 tp = 8 decode: PaLM 비교의 −41~−60%를 설명할 남은 후보입니다. Kaggle v5e-8 배정을 기다리고 있습니다.
  • while 루프 반복 비용: --only loopk 측정 스크립트를 만들었고, Colab 실행이 필요합니다.
  • Ramulator2 연동의 스트림 시작 지연: 연쇄 실행에서 Ramulator2가 analytic보다 큰 오차(23.4%)를 보이는 원인입니다. 레이어 단위로 장치를 이어서 쓰는 연동이 필요합니다.
  • 256×256 MXU 세대: v6e나 Ironwood는 Kaggle에 없어, TRC나 유료 Cloud TPU가 필요합니다.
