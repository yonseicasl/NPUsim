# Phase 4 external energy reference — provenance

`cacti_sram_reference.csv` is generated, not hand-entered. Everything needed to reproduce it:

| item | value |
| --- | --- |
| tool | CACTI 7 |
| source | https://github.com/HewlettPackard/cacti.git |
| commit | `1ffd8dfb10303d306ecd8d215320aea07651e878` (2017-06-19) |
| build | `make -j8`, g++ (system), no source modifications |
| base config | the repository's own `cache.cfg`, with only the fields below overridden |
| overrides | `-size (bytes)`, `-block size (bytes)`, `-technology (u)`, `-output/input bus width`, `-cache type "ram"`, `-associativity 1` |
| cell / peripheral type | `itrs-hp` (as shipped in `cache.cfg`) |
| operating temperature | 360 K (as shipped) |
| technology nodes | 45 nm, 32 nm, 22 nm |
| units | CACTI reports nJ/access and mW; the CSV stores pJ/access and mW |

Geometries are the ones the NPUsim configs DECLARE, so the reference answers "what would an SRAM
of the size this config claims actually cost", not "what number would make the model agree".

Accelergy (https://github.com/Accelergy-Project/accelergy, commit `6911d156`, version 0.4) and its
CACTI plug-in were also installed and exercised. They are not used as the reference source: the
plug-in's substance IS CACTI, so it would report the same numbers with extra plumbing. Accelergy's
`accelergy-table-based-plug-ins` was examined for an independent MAC and DRAM figure and REJECTED as
a reference — `intmac.csv` and `DRAM.csv` there are templates carrying two illustrative rows each
(45 nm 16-bit MAC = 3 pJ, LPDDR4 64-bit read = 100 pJ) with no stated derivation. They are not a
calibrated dataset and are not cited as one here.

## DRAM reference — DRAMsim3

`dramsim3_dram_reference.csv` is generated by running the vendored DRAMsim3, not hand-entered.

| item | value |
| --- | --- |
| tool | DRAMsim3, vendored at `ext/DRAMsim3` (pinned in `npusim.sh` to `29817593`) |
| binary | `make dramsim3main.out` in that tree, unmodified sources |
| device files | the repository's own `configs/*.ini` — JEDEC datasheet IDD currents and VDD |
| devices | exactly the six that NPUsim configs name in `dram_config` |
| run | `-c 200000 -s stream`, per-command energy = reported energy / command count |
| unit conversion | DRAMsim3 accumulates V x mA x cycles, i.e. mW-cycles; multiplying by tCK (ns) gives pJ. Confirmed two ways: its own `average_power` equals `total_energy / num_cycles`, and `read_energy / num_read_cmds` reproduces `VDD*(IDD4R-IDD3N)*burst_cycle*devices` exactly |

The reference is INDEPENDENTLY re-derived by `check.py` P4-6 from each device file's own parameters,
so it is not merely "whatever the tool printed" — a corrupted row is detected.

DRAMsim3 models the DRAM device. It does not model the off-chip link, so NPUsim's
`[dram] transfer_energy` is not covered here and is left at its declared value.

## Still not calibrated: MAC compute energy

Neither CACTI nor DRAMsim3 models an arithmetic unit, and Accelergy's table plug-in carries only
template rows, so `computation_energy` / `mac_energy_*` remain uncalibrated in every fixture
including the calibrated one. Closing it needs synthesis of an int8 MAC at a stated node (the tree
at `ext/chipyard` is the obvious starting point) or a published per-MAC figure with its node.

## Not done: Simba

Simba (Shao et al., *Simba: Scaling Deep-Learning Inference with Multi-Chip-Module-Based
Architecture*, MICRO 2019, DOI 10.1145/3352460.3358302) would be the right external reference for
the RE6 NoP link-energy contract, which has none. It could not be used: the DOI returns HTTP 403 and
the paper is not on arXiv, so no figure from it is verifiable here. Remembered numbers were NOT
written into a reference file — a golden reference that cannot be traced to a source is worse than no
reference, because it looks like validation.

To close it, the following are needed from the paper (or its VLSI/JSSC companion):
  * NoP energy per bit or per package-link traversal, and the technology node,
  * the PE/GLB access energies for the same node, to place the NoP figure in scale,
  * the chip-count and array geometry each figure was measured at.
With those, `validation/phase4/check.py` gains a NoP arm exactly like its SRAM arm.

## 2026-08-26 — nv_small SRAM rows

Same tool, commit, base config, override set, cell type and temperature as the original
rows (see the table above). Generated by `gen_nvdla_sram_rows.py <cacti-checkout>`;
geometries come from the GENERATED nv_small RTL macros, not from NPUsim's config:

| row | macro | geometry | note |
| --- | --- | --- | --- |
| `nvdla_cbuf_bank` | `nv_ram_rws_256x64` | 2048 B, 8 B block, 64 b bus | the CBUF bank macro; 32 banks x 2 macros = 128 KiB |
| `nvdla_cacc_assembly` | `nv_ram_rws_16x256` | 512 B, 32 B block, 128 b bus | CACTI finds no valid organization at the physical 256 b bus for an array this small; the 128 b row is consumed PER BYTE by the per-byte accumulator key, which the narrower bus leaves unchanged to first order |

Consumption in `configs/accelerators/nvdla_small_cacti22.cfg` (all derivations stated in
its header): CBUF per-access read/write at the 64 b line for dat/out and 8x for the
512 b weight line (8 banks in parallel); CACC as the mean of read/write per byte;
leakage as macros-per-declared-partition x mW at the 1000 MHz clock; DRAM from the
existing `DDR3_8Gb_x16_1600` row at 8 B per beat. NOT calibrated and deliberately
undeclared (the unpriced/undercount machinery fires): MAC compute, operand registers,
CMAC adder tree, stripe/setup control, NoC wires, CACC delivery buffer (544 B geometry
rejected by CACTI), MCIF FIFOs, clock network. The RTL is TSMC16FFLR; 22 nm is the
nearest CACTI node, as with gemmini_cacti22.
